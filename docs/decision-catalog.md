# Decision catalog

This catalog records the non-obvious decisions behind important conditionals
and boundaries. Code remains authoritative, but a change that reverses one of
these decisions must update this document explicitly.

| ID | Decision | Why the condition exists | Consequence | Primary source area |
| --- | --- | --- | --- | --- |
| ACCESS-001 | Applications call a consumer BFF, never Access directly. | The integration credential, session token, and flow capability are server bearer authority. | Mobile/web receives semantic state only. | `Api/Authentication`, consumer SDK adapters |
| ACCESS-002 | Realm and environment come from the integration credential. | Caller-selected tenancy would permit cross-realm reads and mutations. | Route payloads never elevate or replace authenticated scope. | `IntegrationClientAuthenticator`, all stores |
| ACCESS-003 | Registration and product sessions have different purposes. | A person may control a credential while required registration policy remains incomplete. | Registration sessions can continue registration but cannot authenticate consumer product endpoints. | `IdentitySession`, email/password service |
| ACCESS-004 | `applicationClientKey` is public; its UUID is internal. | Recreating topology must not change build configuration, and a public selector must not be mistaken for authorization. | Keys select metadata only inside credential scope. | `ApplicationClient`, configuration endpoint |
| ACCESS-005 | Policy and providers belong to each app environment. | Global provider defaults can leak credentials or behavior between tenants. | One protected manifest carries policy, providers, bypass, and public configuration. | `AppEnvironmentConfiguration` |
| ACCESS-006 | Disabled verification cannot name a provider. | Retaining an ignored provider implies verification and unnecessarily stores secret configuration. | Bootstrap rejects the inconsistent document. | `IdentifierVerificationPolicy` |
| ACCESS-007 | A disabled identifier cannot be required or verified. | The combination has no valid runtime journey. | Configuration fails before a user reaches an impossible state. | `IdentifierAccessPolicy` |
| ACCESS-008 | Native application clients require application ids. | Android/iOS package identity is part of platform metadata; Web has no equivalent. | Android/iOS without an id are rejected; Web may omit it. | `ApplicationClient.Configure` |
| ACCESS-009 | SMS Retriever app hash is Android-only. | It is derived from Android package and signing certificate and has no iOS/Web meaning. | A hash on another platform is rejected instead of silently ignored. | `ApplicationClient.Configure` |
| ACCESS-010 | Exact replay requires request id and identical payload hash. | An id alone could accidentally or maliciously name different operations. | Same input reproduces the stored result; different input conflicts. | `AccessFlowRequest`, `IAccessFlowStore` |
| ACCESS-011 | Available actions come from the current snapshot. | The server, not UI assumptions, owns policy and valid transitions. | A client cannot manufacture an action or execute one from a stale revision. | `AccessFlowProtocol`, `AccessFlowService` |
| ACCESS-012 | Every accepted transition checks `expectedRevision`. | Parallel tabs, retries, or delayed responses must not overwrite newer state. | Stale actions produce a revision conflict and require refresh. | `AccessFlow`, flow store commits |
| ACCESS-013 | External delivery uses reserve, perform, finalize/fail. | SMTP and SMS cannot share the PostgreSQL transaction; sending first can leave an untracked effect. | Every attempted effect has durable state and explicit retry meaning. | `AccessFlowRequest`, recovery and flow services |
| ACCESS-014 | AccessFlow phone confirmation trusts the local OTP hash. | Access generated the custom code; a second provider decision can expire or disagree after valid delivery. | Twilio transports the code but does not re-authorize a local match. | `AccessFlowService`, proof challenge store |
| ACCESS-015 | Social or phone conflicts do not silently merge identities. | Matching contact metadata does not prove permission to combine two identity histories. | Only explicit server-advertised resolution actions may move a proven identifier or recover an identity. | social service, phone conflict flow |
| ACCESS-016 | Flow data-subject links are append-only. | Ownership can change and snapshots contain historical personal data. Current foreign keys or text search cannot prove erasure reachability. | Deleting any linked identity deletes the entire related flow but does not delete the other identities linked to that flow. | `AccessFlowDataSubject`, current identity store |
| ACCESS-017 | Provider availability does not block hard deletion. | Erasure is a local data obligation and providers are independent failure domains. | Access purges PostgreSQL without waiting for SMTP, SMS, or Twilio. | `ICurrentIdentityStore.TryDeleteAsync` |
| ACCESS-018 | Access and consumer deletion are separate transactions. | Independent databases cannot honestly promise atomic commit. | Each consumer owns ordering, retries, and operational repair. | service boundary and consumer adapter |
| ACCESS-019 | Email verification is environment policy, not a universal rule. | Products can deliberately accept a syntactically valid unique email without possession proof. | Documentation must not infer `emailVerifiedAt` where policy disables verification. | access policy, email registration/change |
| ACCESS-020 | The original consumer baseline exposed no administrative API; the separately approved backend is now defined by ACCESS-095 through ACCESS-099. | Consumer backoffices and Bullgate administration remain separate products and trust models. | Constants alone do not expose endpoints; administrative routes require their separate caller scheme and exact key. | API route map, `AccessPermission`, `administration.md` |
| ACCESS-021 | Bullgate Access is licensed under GNU AGPL-3.0-or-later. | Network-service modifications must remain available to the users interacting with the modified service, while the later-version option preserves future license compatibility. | Recipients may choose version 3 or a later FSF version; distribution and hosted modifications must comply with the selected version. | `LICENSE`, README license section |
| ACCESS-022 | The Bullgate Access product remains open source; Bullgate Cloud may charge for managed hosting and operations. | Revenue comes from running the service reliably rather than withholding Access functionality from self-hosted users. | Paid hosting does not create a proprietary Bullgate Access edition or remove AGPL obligations. | `docs/open-source-governance.md` |
| ACCESS-023 | External contributions use DCO 1.1 without a CLA. | Per-commit provenance certification is low-friction and matches the decision to keep contributed Access functionality open source. | Every contributed commit requires `Signed-off-by`; contributors retain copyright, so unilateral proprietary relicensing is not assumed. | `DCO`, `CONTRIBUTING.md` |
| ACCESS-024 | Torphi Contise Tratamento de Dados Ltda holds copyright in the original project. | Company ownership aligns stewardship with the entity operating the paid hosted service. | Project notices name the company; DCO contributors retain copyright in their own contributions. | `COPYRIGHT.md`, open-source governance |
| ACCESS-025 | Security reports use a private company-controlled contact with five-business-day acknowledgement and ten-business-day initial-assessment targets. | Public disclosure can enable exploitation, while explicit response targets set realistic expectations for reporters. | Reports go to `marco@torphi.com.br`; the targets are not remediation guarantees or an SLA. | `SECURITY.md`, open-source governance |
| ACCESS-026 | Protected environment configuration is authenticated against its environment id and format version. | Encryption alone would not prevent a valid ciphertext from being moved to a different security scope or interpreted under an incompatible format. | Copying, relabeling, tampering, or decrypting with the wrong installation key fails before configuration is returned. | `AppEnvironmentConfigurationProtector` |
| ACCESS-027 | Bootstrap is a single-writer, atomic topology reconciliation. | Parallel read-then-create operations can race even when individual natural keys are unique, and partial commits can separate policy from permissions or credentials. | A transaction-scoped PostgreSQL advisory lock serializes bootstrap; topology and protected configuration commit together. | `BootstrapTopologyHandler`, `AccessTopologyStore` |
| ACCESS-028 | Only an integration credential hash is retained after one-time issuance. | Recoverable server credentials increase disclosure impact; caller-selected scope would allow privilege escalation. | The clear `bgic_...` token is returned only at creation; its UUIDv7 is a lookup selector and its 32-byte random secret is hashed, while authentication derives fixed scope from active topology and uses constant-time comparison. | integration credential token, issuer, secret, and authenticator |
| ACCESS-029 | Proof and recovery transitions are reserved by partial unique indexes. | Two workers can observe the same previous state before either writes, and external delivery cannot join the database transaction. | Historical terminal rows remain available, but only one worker can own each pending, active, or confirming operation in the protected scope. | proof and phone-recovery EF configurations |
| ACCESS-030 | Provider adapters expose narrow application outcomes while retaining provider-specific diagnostic behavior. | SMTP, Twilio, Google, and Apple are independent protocols whose errors may contain secrets, contact data, or unstable provider detail that must not become an application contract. | Caller cancellation remains distinct where observable; SMTP returns `false` and logs no caught exception detail, Twilio retains status and a parseable error code while discarding its arbitrary body, and social validators return no assertion for their documented rejection classes. | SMTP, Twilio, Google, and Apple adapters |
| ACCESS-031 | An app environment may combine only an app and realm from its own workspace. | Checking valid UUIDs independently would allow accidental cross-workspace topology and break tenancy assumptions. | Composite foreign keys make the shared workspace id part of both relationships. | `AppEnvironmentEntityConfiguration` |
| ACCESS-032 | Identifier uniqueness protects both realm ownership and one-value-per-scheme identity shape. | A unique normalized value prevents multiple owners, but does not alone prevent one identity from accumulating ambiguous primary identifiers of the same kind. | PostgreSQL enforces one owner per realm/scheme/value and one value per realm/identity/scheme. | `IdentityIdentifierConfiguration` |
| ACCESS-033 | Exact request replay is anchored to an immutable stored revision. | Returning the current flow snapshot on retry would change the historical result after later transitions and could change issued-session interpretation. | A committed request references its exact result revision; replay reads the durable winning request instead of rebuilding success from the current command, and only one pending external request may own a flow at a time. | `AccessFlowRequestConfiguration`, `AccessFlowService.Replay` |
| ACCESS-034 | Topology deletion is restricted while identity-owned credentials and sessions cascade on hard deletion. | Installation topology is operational configuration with explicit lifecycle, whereas identity erasure must remove dependent authentication material. | Workspaces, environments, clients, and provider scope are not casually cascade-deleted; deleting an identity removes its authenticators and sessions after related flow graphs are handled. | topology and identity EF configurations |
| ACCESS-035 | Ordinary bearer tokens are random, while AccessFlow capabilities and terminal sessions are deterministic scoped HMAC outputs. | Ordinary issuance needs unrecoverable fresh authority; exact flow replay must reproduce the original clear result without storing clear bearer material. | All persistent token values remain hashes; replay derives the same terminal token from server-owned scope and verifies its hash against the session referenced by the committed request before returning clear authority. | opaque token services, `HmacAccessFlowTokenService`, flow replay |
| ACCESS-036 | Token parsers accept only one fixed prefix, length, UUID rendering where applicable, and unpadded Base64url alphabet for each supported shape. | Alternate or malformed representations add ambiguity and unnecessary database work without granting authority. | Malformed input is rejected before hashing or lookup; integration credentials additionally require a canonical lower-case UUIDv7 and canonical final Base64url character, while valid shape still requires hash or HMAC authority validation. | integration credential, session, reset, and flow token services |
| ACCESS-037 | Identity contact reads require the identity id and stored identifier to match the authenticated realm. | A route UUID is a selector controlled by the caller, not proof of realm ownership. | Cross-realm UUIDs behave as absent even if the identifier exists; requests cannot override integration-client scope. | `IdentityEmailStore`, `IdentityPhoneStore` |
| ACCESS-038 | Social provider assertions are bound to the client id protected in the target app environment. | A correctly signed token issued for another application is not authority inside this environment. | Google requires matching `aud` or `azp`; Apple requires the configured audience plus Apple issuer, signature, and lifetime validation. | Google and Apple identity validators |
| ACCESS-039 | Provider subject, not provider e-mail, is the stable social credential key. | E-mail is mutable contact metadata and a matching value does not prove permission to reuse or merge an identity. | Accepted provider claims require subject and e-mail, but only provider/subject ownership resolves an existing social identity. | social validators and `SocialAccessService` |
| ACCESS-040 | HTTP authentication creates scope claims only from a fully authenticated integration credential. | Route and body values are caller-controlled, while exposing individual credential failures would aid probing. | Exactly one Bearer value is accepted; malformed, incorrect, expired, revoked, inactive-scope, or unknown-permission candidates receive the same minimal HTTP 401 challenge, while a valid credential with no or insufficient grants authenticates and receives HTTP 403 from permission policy. | API authentication handler and policies |
| ACCESS-041 | Bootstrap CLI standard output is one machine-readable result; diagnostics use standard error. | Host logs or status text mixed into JSON would break automation, and newly issued clear credentials require secret handling. | Default host log providers are removed; automation must capture successful stdout securely and must not treat it as an ordinary log. | CLI `Program.cs` |
| ACCESS-042 | Manifest version 2 is strict, case-sensitive, and fully shape-validated before domain conversion. | Ignored typos, null nested objects, or guessed future formats could silently weaken policy or apply unintended topology. | Unknown and incorrectly cased properties, unsupported versions/platforms, and invalid nested shapes fail before bootstrap begins. | `BootstrapManifest`, CLI JSON options |
| ACCESS-043 | Reapplying bootstrap checks existing natural-key resources for compatibility instead of silently mutating their identity or permissions. | A declarative convenience operation must not re-scope trusted clients or topology under an existing stable key. | Compatible resources are reused; incompatible definitions are rejected, and existing clear credentials are never recovered or reissued. | `BootstrapTopologyHandler` |
| ACCESS-044 | Access transport DTOs may contain server bearer material and are not automatically application-safe. | Session tokens, flow capabilities, and reset authority grant access even when adjacent snapshot or configuration data is public. | The BFF retains bearer fields and projects a smaller semantic application response; DTO placement never reclassifies a secret. | endpoint response records, integration guide |
| ACCESS-045 | Session introspection and revocation use uniform HTTP success envelopes. | Revealing whether a submitted opaque token names a session row adds an unnecessary probing signal and makes safe retries harder. | Introspection returns HTTP 200 with `active: false`; revocation returns HTTP 204 for every token outcome, may stamp the first explicit revocation on an expired matching row, and never rewrites an existing revocation time. | email/password endpoints, `IEmailPasswordAccessStore.RevokeSessionAsync` |
| ACCESS-046 | Phone recovery locks the identity before its challenge and revalidates every preliminary lookup. | Candidate discovery, provider delivery, and confirmation cross transaction boundaries; treating an earlier read as authority would allow stale ownership, policy, cooldown, or challenge state to win. | Recovery transitions serialize per identity, use a deterministic lock order, and return collapsed invalid outcomes when locked state no longer qualifies. | `PhonePasswordRecoveryStore` |
| ACCESS-047 | A password-recovery URL is clear bearer authority even when wrapped in a delivery DTO. | Possession of the URL can replace an identity password, and SMTP cannot participate in the token-issuance transaction. | Only the token hash persists; the clear URL remains inside the intended e-mail boundary, while trusted orchestration receives only a token id for bounded invalidation. | e-mail recovery service and sender |
| ACCESS-048 | Replacing the primary e-mail clears its verification evidence and invalidates every outstanding password-recovery path. | Verification belongs to the old value, while previously issued e-mail tokens or phone challenges were authorized from an earlier identity snapshot. | The new e-mail starts unverified; active reset tokens are consumed and open phone recovery challenges become superseded in the same transaction. | `CurrentIdentityStore.TryChangeEmailAsync` |
| ACCESS-049 | Provider-delivery records are sensitive even when they are internal application or transport DTOs. | Phone/e-mail delivery objects may contain personal destinations, clear OTPs, reset URLs, or provider credentials; record shape and internal visibility do not make those values safe to observe. | Delivery objects stay inside the adapter boundary; logs use opaque provider references and structured outcome codes, never the complete request or raw provider body. | verification and recovery sender contracts |
| ACCESS-050 | A successful password change keeps the authorizing product session but revokes every other session and consumes active reset tokens. | The current request needs a usable post-change session, while older sessions and recovery links remain alternate credential paths that may be stale or compromised. | Password replacement and invalidation commit together; social authenticators remain linked and a social-only identity may add its first password without presenting an old password. | email/password service and store |
| ACCESS-051 | Re-linking the same provider subject is idempotent, but a different subject or an already owned subject is a conflict. | Provider e-mail may change and is only metadata; silently replacing or transferring the stable subject would move account authority. | The same subject may refresh its provider e-mail, while provider-per-identity and provider-subject ownership remain transactionally unique; unlink also preserves a final authenticator. | social service and store |
| ACCESS-052 | AccessFlow challenge rate counting excludes challenges whose provider delivery failed. | A delivery failure produces no usable proof attempt for the person; charging it against the AccessFlow quota would let a provider outage lock out a legitimate journey. | `DeliveryFailed` rows remain durable for diagnosis but do not count toward the recent-challenge limit; this rule is specific to AccessFlow and must not be assumed for other recovery stores. | `AccessFlowStore.CountRecentChallengesAsync` |
| ACCESS-053 | Reserving a replacement AccessFlow proof challenge does not immediately supersede the previous active challenge. | The new provider delivery may fail after reservation; invalidating the old code first would leave the person with no usable proof because of a provider failure. | Older active challenges are superseded only when replacement delivery finalizes; failed delivery closes only the new pending challenge and request. | AccessFlow proof challenge reserve/finalize/fail methods |
| ACCESS-054 | AccessFlow phone confirmation reserves the locally accepted OTP before final persistence; Twilio is not a second proof authority. | Local hash comparison and the final ownership transaction are separated by orchestration work, so parallel requests must not consume the same challenge or act on changed phone ownership. | `Confirming` plus a pending request grants one finalizer; commit rechecks revision, attempts, and owner under locks, while failed finalization releases a still-valid reservation for a safe retry. | AccessFlow phone confirmation methods |
| ACCESS-055 | Explicit phone transfer combines phone-possession proof with knowledge of the previous owner's exact normalized e-mail; it does not prove possession of that mailbox. | A masked hint plus limited comparison attempts adds a conflict-resolution check without pretending that no-message e-mail comparison is cryptographic or delivery proof. | Mismatches consume a concurrency-protected attempt budget; a match still commits only after the previous identity, phone ownership, prior phone proof, and source session are revalidated under locks. | `AccessFlowService.TransferPhoneAsync`, `AccessFlowStore.TryTransferPhoneAsync` |
| ACCESS-056 | Previous-identity recovery reserves its idempotent action before e-mail delivery and finalizes the flow only after provider acceptance. | Database state and an external e-mail provider cannot commit atomically, while replay still needs durable ownership and outcome for the side effect. | Reserve and finalize revalidate the same locked identity, conflict, phone, and proof facts; later failures close the reservation and, when a token id was returned, trigger bounded best-effort token invalidation. Provider acceptance is not inbox-delivery proof. | previous-identity recovery reserve/send/finalize/fail orchestration |
| ACCESS-057 | A normal terminal AccessFlow action commits its result and new product-session hash only while revoking the exact source session in the same transaction. | Returning new authority while old flow authority remains independently usable would split the security outcome and make a failed commit ambiguous. | Registration completion additionally revokes other registration sessions for the same identity and environment; phone management rotates only its source product session, while deterministic issuance supports exact replay without storing the clear bearer. | terminal AccessFlow completion methods |
| ACCESS-058 | `skipRegistration` is authorized only by its presence in the current server-owned snapshot. | Optional phone policy permits omission during registration, but a client-visible step name or an action retained from an older revision is not authority. | The action is emitted only for `continueRegistration` when phone is not required; action id, type, and revision must match the persisted snapshot, and `managePhone` never receives a skip action. | `AccessFlowService.ActAsync`, snapshot factories |
| ACCESS-059 | AccessFlow expiration is a revisioned terminal transition that releases the active-flow slot without revoking the source identity session. | A wall-clock observation can race with a valid action, while a still-active source session must be able to start a replacement journey after stale state is closed. | Expiration requires the exact current revision, records an immutable terminal snapshot, and closes pending local request/challenge state atomically; it cannot retract an external provider effect already accepted. | flow expiration and stale-flow replacement methods |
| ACCESS-060 | An active AccessFlow is resumed only under the same complete source and client binding; preliminary candidate reads never authorize creation. | The source-session/intent slot can race, and sharing a session selector must not transfer a journey across identity, realm, environment, registration context, integration client, public application client, or protocol boundaries. | `TryCreateAsync` revalidates authority under locks and the partial unique index arbitrates parallel creators; compatible resume records a start request at the existing revision and returns its persisted snapshot without rebuilding policy. | `AccessFlowService.StartAsync`, `AccessFlowStore.TryCreateAsync` |
| ACCESS-061 | A live pending external-operation reservation blocks different AccessFlow actions; a new request id does not bypass effect ownership. | SMS and e-mail workers can outlive an HTTP request, so immediate retry under a new id could duplicate delivery, while an abandoned reservation must not block the flow forever. | The exact request finalizer may continue its reservation; challenge-backed ownership follows challenge lifetime, request-only e-mail recovery uses a one-minute grace window, and locked reconciliation closes stale local state before another transition proceeds. | `AccessFlowStore.LoadActiveFlowAsync`, reservation reconciliation |
| ACCESS-062 | A flow UUID is only a selector; read and action authority require authenticated integration scope plus exactly one capability bound to the flow, integration client, and environment. | Distinguishing missing rows from malformed, wrong-scope, or non-matching capabilities would make flow identifiers an enumeration signal. | The BFF retains capability bearer material, repeated capability headers are rejected as ambiguous, and all unsuccessful capability/scope resolution collapses to `flow-not-found`. | `AccessFlowService.GetAsync`, `AccessFlowService.ActAsync`, `AccessFlowEndpoints` |
| ACCESS-063 | Phone normalization accepts only an already canonical plus-prefixed ASCII-digit shape; it does not infer regional formatting or prove the number exists. | Guessing country rules or silently rewriting punctuation can make two inputs map unexpectedly, while syntactic acceptance must not be confused with delivery or possession evidence. | Outer whitespace is trimmed, then `+` plus 8–15 digits with a non-zero first digit is required; allocation, reachability, and possession remain outside normalization, and proof is enforced separately when policy enables verification. | `PhoneValue.TryNormalize`, phone identifier flows |
| ACCESS-064 | Integration-credential activity is the conjunction of its client, environment, app, realm, and workspace activity, independent of secret expiry and revocation. | Operators need to quarantine an entire topology branch without rewriting every descendant secret or falsifying credential lifecycle history. | Any inactive ancestor rejects authentication while hash, expiry, and revocation metadata remain unchanged; a credential must pass both effective topology activity and its own lifecycle checks. | `IntegrationClientAuthenticationStore`, `IntegrationClientAuthenticator` |
| ACCESS-065 | Successful password login derives session purpose from the target environment's current registration context, not from password possession alone. | Proving an authenticator establishes identity control but does not prove that required or explicitly skippable registration decisions were completed. | An open registration context yields a registration-purpose session that can continue the journey but cannot authenticate product endpoints; only a closed or absent context yields product authority. | `EmailPasswordAccessService.LoginAsync`, session resolution |
| ACCESS-066 | Enabling optional phone collection still keeps new registration open until the person collects a phone or executes the advertised skip action. | Optional means the person may decline inside the server-owned state machine, not that the service may silently assume a choice during credential registration. | Registration completes immediately only when no phone journey or e-mail verification remains; an enabled optional phone yields registration authority and an explicit `skipRegistration` path. | `EmailPasswordAccessService.RegisterAsync`, AccessFlow snapshot factories |
| ACCESS-067 | Social authentication resolves identity ownership only by realm, provider, and provider subject; an asserted e-mail never selects or merges an existing identity. | Provider e-mail is mutable contact metadata, while silently merging on a matching address could transfer two independent identity histories. | An unknown provider subject starts new registration; if its primary e-mail is already owned, creation returns a conflict instead of reusing that identity. | `SocialAccessService.AuthenticateAsync`, `SocialAccessStore.FindByProviderAsync` |
| ACCESS-068 | Social authentication and social linking have intentionally different feature gates. | Authentication may create a primary e-mail identifier, while linking starts from an existing product identity and retains its current primary e-mail. | Authentication requires both e-mail identity and the provider enabled; linking requires the provider enabled and stores the asserted e-mail only as provider metadata. | `SocialAccessService.GoogleAsync`, `AppleAsync`, `LinkGoogleAsync`, `LinkAppleAsync` |
| ACCESS-069 | Provider-specific validation decides when a social e-mail may become a verified primary identifier. | A signed token is not sufficient until the environment audience and required identity claims satisfy the selected provider contract. | Google requires a non-empty subject and explicitly verified e-mail; Apple requires issuer, signature, lifetime, environment audience, non-empty subject, and non-empty e-mail but currently performs no separate `email_verified` claim check. | `GoogleIdentityValidator`, `AppleIdentityValidator`, `SocialAccessService.CreateRegistrationAsync` |
| ACCESS-070 | Social unlink serializes the final-authenticator check by locking the identity and evaluating password plus social credentials in one transaction. | Two concurrent removals could each observe another login path and together leave the identity inaccessible. | Missing-provider and last-authenticator outcomes change nothing; only a locked state that retains another authenticator may delete the requested social credential. | `SocialAccessStore.UnlinkAsync` |
| ACCESS-071 | E-mail reset authority is persisted before SMTP submission, and provider outcome does not rewrite that issuance history. | PostgreSQL and SMTP cannot commit atomically, while a timeout, rejection, or acceptance does not prove inbox delivery or token absence. | Trusted orchestration receives only the token id for bounded invalidation; public recovery hides identity, throttling, configuration, issuance, and delivery outcomes behind HTTP 202, and failed delivery may still consume issuance quota. | `EmailPasswordRecoveryService`, `IPasswordRecoveryEmailSender` |
| ACCESS-072 | Successful password reset consumes the presented token while revoking every identity session and every competing active reset token in one transaction. | Recovery authority may indicate account compromise, and any older session or recovery message is an alternate credential path that must not survive the new password. | The preliminary active-token read is only a fast check; identity and token are locked and revalidated before password replacement and all invalidations commit together. | `PasswordResetService.ResetAsync`, `PasswordResetStore.TryResetPasswordAsync` |
| ACCESS-073 | Phone recovery initiation collapses ownership absence, hourly rate limit, and resend cooldown into the same accepted timing envelope, but not every failure. | Those three states depend on whether a person owns the phone or has recent recovery history; exposing them separately would create an account oracle. | Malformed input, invalid application-client selection, disabled policy, and provider unavailability remain explicit errors, while an unreserved ownership-sensitive request returns the same advertised expiry and resend times as a reserved request. | `PhonePasswordRecoveryService.RequestAsync`, phone recovery endpoints |
| ACCESS-074 | Phone recovery separates reservation, usable delivery, exclusive confirmation, and reset-token issuance into durable states. | SMS and provider approval happen outside PostgreSQL, so treating an earlier side effect as a committed later state would permit premature or duplicate proof consumption. | Only `Active` accepts code checks, `Confirming` grants one provider finalizer, and `Completed` commits provider approval with the reset-token hash; rollback restores only an unexpired provider-backed predecessor. | `PhonePasswordResetChallenge`, `PhonePasswordRecoveryStore` |
| ACCESS-075 | Phone-recovery rate and cooldown accounting is per identity across environments and includes terminal durable requests rather than only usable delivered challenges. | Ignoring other environments or failed, exhausted, or superseded reservations would let repeated provider failures or replacements reopen abuse-control capacity. | Every challenge for the identity created inside the hourly window counts, and resend availability follows that identity's latest request regardless of environment or later state; this intentionally differs from AccessFlow proof-delivery counting. | `PhonePasswordRecoveryStore.TryReserveAsync` |
| ACCESS-076 | Phone-recovery code validity is decided by Access before Twilio lifecycle approval. | Access generated the custom code and owns its hash and attempt budget; delegating proof truth back to delivery infrastructure would create two competing authorities. | The store compares hashes in constant time and reserves `Confirming`; only then does orchestration mark the provider resource approved, while wrong or ineligible states remain locally collapsed to `invalid-code`. | `PhonePasswordRecoveryStore.TryBeginConfirmationAsync`, `TwilioPhoneVerificationSender.ApproveAsync` |
| ACCESS-077 | Constrained reset-token issuance counts all durable reset authority for the identity across environments and recovery channels. | Limiting only successful delivery or still-active tokens would let repeated issuance, immediate use, or cross-channel switching reopen capacity inside the same window. | Candidate lookup remains preliminary; the identity lock revalidates exact e-mail ownership and eligibility, then counts every token created since the inclusive window boundary before inserting another hash. | `PasswordResetStore.TryIssueAsync`, `PasswordResetIssueConstraint` |
| ACCESS-078 | Repeating the current canonical primary e-mail is an idempotent success, while an actual replacement clears verification and invalidates recovery authority. | A no-op must not erase valid proof or recovery state, but evidence and issued recovery paths authorized from the old value cannot survive a contact change. | Exact normalized equality returns the current snapshot without writing; a different value commits uniqueness, clears e-mail verification, consumes active reset tokens, and supersedes open phone-recovery challenges together. | `CurrentIdentityService.ChangeEmailAsync`, `CurrentIdentityStore.TryChangeEmailAsync` |
| ACCESS-079 | A stored phone and phone-possession proof are separate read facts. | Treating an unverified phone as absent would hide current identity state, while treating its presence as verified would invent authority. | Realm-scoped phone reads return HTTP 200 with nullable `verifiedAt` when the identifier exists; only collapsed identity/contact absence returns `identity-not-found`. | `IdentityPhoneReader`, `IdentityPhoneEndpoints` |
| ACCESS-080 | Abandonment is retained lifecycle history for a provisional identity, not user-requested erasure. | Recovery must close the interrupted registration identity without pretending its row was deleted, while an erasure request must actually remove attributable Access data. | Previous-identity recovery marks the provisional identity `Abandoned` and removes its usable access material; `DELETE /v1/account` follows the separate hard-delete transaction. | `Identity.Abandon`, `AccessFlowStore.TryFinalizePreviousIdentityRecoveryAsync`, `CurrentIdentityStore.TryDeleteAsync` |
| ACCESS-081 | Password hashing, rotation authority, and persisted credential state have separate owners. | A domain entity cannot prove a clear password or reset bearer merely because it receives a replacement hash, and duplicating the hasher's encoded-format rules would couple the domain to one implementation. | Application services authorize the change, `IPasswordHashService` creates or verifies the encoded value, and `PasswordCredential` stores that opaque value with timestamps. | `PasswordCredential`, `IPasswordHashService`, password change and reset services |
| ACCESS-082 | Registration-context closure is monotonic and exact terminal repetition preserves the first closure time. | Completion and abandonment represent different identity-continuity outcomes; overwriting one with the other or restamping retries would make durable history depend on transport timing. | `Open` may become `Completed` or `Abandoned`; repeating that same outcome is a no-op, while attempting the opposite terminal outcome throws. | `RegistrationContext.Close`, registration finalization transactions |
| ACCESS-083 | Password-reset consumption and compensating invalidation share one terminal `UsedAt` marker. | Both outcomes must end bearer authority, but the token row is not an audit claim that a password actually changed; compensation also cannot roll back provider delivery. | Domain consumption is strict, retry-safe invalidation conditionally stamps only an unused unexpired row, and a populated `UsedAt` is interpreted only as no remaining reset authority. | `PasswordResetToken.MarkUsed`, `PasswordResetStore.TryInvalidateAsync`, recovery compensation |

## How to use this catalog during review

When reviewing a new `if`, transaction branch, or exception mapping:

1. identify the protected invariant and owning component;
2. link it to an existing decision or add a new decision id;
3. document the failure behavior, not only the accepted branch;
4. check whether the condition is also enforced by schema or transactional code;
5. update AI evaluation cases if an answer-visible contract changed.

Do not put decision ids on every code line. Use them where a future maintainer
could reasonably remove a condition as "redundant" and break a non-local rule.
